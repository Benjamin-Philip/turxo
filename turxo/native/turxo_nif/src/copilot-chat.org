You can't safely store a =Transaction<'a>= with a concrete lifetime inside a struct (=TransactionResource=) that's held by a Rustler =Resource=, because the connection (=conn=) can't outlive the struct /and/ be borrowed at the same time.

*Common options:*

*** 1. Don't Store Transaction Directly
Store connection and transaction separately. When you need to operate on the transaction, keep it in a local variable per function invocation, not in the resource. This only really works for very short-lived transactions.

*** 2. Use =Box::leak= (NOT recommended for production)
Some try to "cheat" the borrow checker by doing:
#+begin_src rust

#+end_src
Or using =Box::leak= to get a ='static= reference:
#+begin_src rust

let tx = Box::leak(Box::new(tx));
// Now tx: &'static mut Transaction<'_>
#+end_src
But *this leads to memory leaks* and is unsafe. Should not be used in serious production code.

*** 3. Store Both in Arc<Mutex<>>
You might try "widening" the lifetime by storing both the connection and the transaction together, in the same struct, wrapping everything in some kind of =Arc<Mutex<_>>=, and /never/ exposing a reference to the connection while the transaction exists. Even this is tricky, as Rust's type system doesn't "forget" the lifetimes. You'd typically use an enum:
#+begin_src rust

    conn: Option<Connection>,
    tx: Option<Transaction<'a>>,
}
#+end_src
But you'd still have to only ever move the transaction out, use it, then return it—can't safely leave it stored for longer.

*** 4. Use "Connection as Resource" pattern
You don't implement a separate resource for the transaction. You give Erlang code a reference to the Connection resource during the Tx, and ensure all transaction commands are invoked on the connection resource, passing a transaction "handle" (an index, or marker) as a state in Rust (like, with an internal =HashMap<Ref, Transaction>=). This is often what diesel and tokio-postgres frontends do. But this is more complicated, especially in a NIF.

*Safest option:* /Don't try to store =Transaction<'_>= as a field inside a resource struct for long-lived Erlang-side handles./  
If you need transactions to be long-lived and accessible as Resource handles, you'll need to *refactor* to store all active transactions somewhere (ex: global or in the Connection struct) and access them via unique IDs.

If you want a quick fix for tests/hacking (with risk!): use =Box::leak= or =transmute= to unsafely give =Transaction<'static>=, but *this is unsafe and leaks memory*.

* Would tokio's RwLock with lock.write_owned be better than a mutex?

**Short answer:*  
Yes, =tokio::sync::RwLock= with =.write_owned()= can be a good choice in async code, /especially/ if you need to sometimes share the resource for reads (e.g., multiple concurrent queries) and exclusive access when writing (e.g., for starting a transaction).  
However, you must understand the tradeoffs compared to a plain async mutex.

---

** Comparing Mutex vs. RwLock

*Mutex*
- Only one task can access the resource at a time—period.
- Simple: all access is exclusive.
- =tokio::sync::Mutex= allows =.lock().await=, and is often the safest/simplest choice when (a) the resource is almost always accessed exclusively or (b) there are mutation/ownership complications (like moving values in and out).

*Tokio RwLock*
- Many concurrent readers—or one exclusive writer (no concurrent readers when writing).
- Good for resources with many reads but infrequent writes.
- With =.write().await=, you get a write /reference/—but if you want to transfer the contained value out, you need =.write_owned().await=.
- =.write_owned()= gives you ownership of the lock and the data. This makes moving the resource out easier.

*** For your use-case (Connection+Transaction):

- If you want to /move/ the Connection out when starting a transaction, =.write_owned()= is helpful: you get the lock ownership and can use =Option::take()=.
- If you want concurrent read access for queries, but exclusive write/take access for transaction-scoped operations, an RwLock is ideal.

** Example

#+begin_src rust
// Initialization
pub struct ConnectionResource(pub tokio::sync::RwLock<Option<Connection>>);

// Query (shared)
async fn query(conn_res: ResourceArc<ConnectionResource>) {
    let read_guard = conn_res.0.read().await;
    let conn = read_guard.as_ref().unwrap();
    // perform query using &conn
}

// Start Transaction (take exclusive ownership)
async fn begin_transaction(conn_res: ResourceArc<ConnectionResource>) -> TransactionResource {
    let write_guard = conn_res.0.write_owned().await; // This gives you full ownership!
    let mut guard = write_guard;
    let conn = guard.take().unwrap(); // Now the Option<Connection> is None in the resource.
    let tx = conn.transaction().await.unwrap();
    // etc: store tx and conn in TransactionResource
}
#+end_src

** Pros of RwLock + write_owned:

- Temporarily "check out" the resource for exclusive ops (move it out, so you can hand it to a transaction).
- Allows shared access for concurrent queries.
- Avoids some lifetime issues: as soon as you move the =Connection= out, the rest of your code can't see or use it until you put it back.

** Cons:

- Slightly more complex than Mutex.
- If you /never/ need concurrent reading, a plain Mutex is simpler.
- Always remember: Using =Option<Connection>= and taking out/moving back can be error-prone if not carefully managed.

** Summary Table

|                | Mutex                     | RwLock (write_owned)         |
|----------------|--------------------------|-------------------------------|
| Concurrency    | Only one at a time       | Many readers, one writer     |
| Move values    | Easy (=.lock().await=)   | Easy with =.write_owned().await= |
| For your case  | Adequate                 | Slightly better if want queries+txn |

---

** *Bottom line*

- *Yes, =RwLock= with =.write_owned()= is perfectly good for async database connections.*
- It especially shines if you want to support concurrent queries, while "taking out" the connection for a transaction.
- Both are appropriate; pick RwLock if you ever want shared access. Pick Mutex for simplicity if all access is exclusive anyway.

---
*TL;DR:*  
*Yes, use =tokio::RwLock= with =.write_owned()= if you want shared query and exclusive transaction semantics.*  
If you only ever access exclusively, =Mutex= is fine.

- If you /must/ implement this as a struct that both owns the connection and transaction, you’ll need to use crates like [ouroboros](https://crates.io/crates/ouroboros) or =pin_project= for proper self-referential structs (advanced!).

*** 3. Practical, safe NIF pattern
*Avoid keeping an open transaction as a resource.* Instead:
- Run a sequence (transaction) of queries inside a single NIF call (the "transaction callback" or "do-atomic").
- The NIF, on the Rust side, starts a transaction, runs all commands, commits, and returns.
- This avoids all resource/lifetime ownership problems, but means multistep transactions handled by Elixir/BEAM directly are not possible.

**** A) Use atomic transaction API
Expose only a single Elixir NIF call that runs a closure of statements within the transaction lifetime, so all lifetimes are in one Rust stack frame.

**** B) Use =Arc<Mutex<Option<Connection>>>= and move connection ownership
When transaction starts:

- Create the transaction.
- Store the connection /and/ transaction in fields of your resource *(see note below! This won’t work with a normal struct due to borrowing!)*.

/But you cannot store both in a struct without advanced patterns, as you noted./

**** C) Use unsafe

** 1. What to Keep In Mind with =unsafe=

- *The =unsafe= here is about "fooling the Rust type system" regarding lifetimes.*
  - You use =std::mem::transmute= (or similar) to convert =Transaction<'_>= into =Transaction<'static>=, /but/ you absolutely must enforce that the transaction is dropped before the connection is reused or dropped.
- If you break this, you get *use-after-free* or *double drop* bugs. These are usually "soundness" (segfaults or silent corruption) errors.
- *No other part of your code may access the Connection while a transaction is alive.*
- You must *never return / move the connection back to BEAM* until after the transaction is finished and dropped.
- *Never expose access to both connection and transaction at the same time* (enforce this in your design).

*** How to minimize risk:

- Put the =unsafe= block in as small and visible a place as possible.
- Assert at runtime (with =debug_assert!= or panics) that you never break the above invariant.
- Document the invariants you are relying on.
- Keep the lifetime of the transaction resource as short as necessary.

---

** 2. Reference Pattern ("Limited Unsafe" Transaction Resource)

Let's show a full pattern using =tokio::RwLock<Option<Connection>>=.

*** Setup: Resource types

#+begin_src rust
use rustler::{ResourceArc, NifStruct};
use tokio::sync::RwLock;
use turso::{Connection, Transaction};

pub struct ConnectionResource(pub RwLock<Option<Connection>>);

pub struct TransactionResource {
    pub tx: Option<Transaction<'static>>, // unsafe transmute, see below
    conn_resource: ResourceArc<ConnectionResource>,
}
#+end_src

*** Begin transaction (NIF)

#+begin_src rust
#[rustler::nif]
async fn conn_transaction(conn_resource: ResourceArc<ConnectionResource>) -> ResourceArc<TransactionResource> {
    // Take the connection out
    let mut guard = conn_resource.0.write().await;
    let conn = guard.take().expect("Connection already checked out!");

    // Start transaction - lifetime is tied to this Conn, but we need to hand it to BEAM
    let tx = conn.transaction().await.expect("Failed to begin transaction!");

    // UNsafe: erase the lifetime
    let tx_static: Transaction<'static> = unsafe { std::mem::transmute(tx) };

    // Store BOTH the transaction and the conn resource (for restoration later)
    ResourceArc::new(TransactionResource {
        tx: Some(tx_static),
        conn_resource,
    })
}
#+end_src

*** Execute in transaction

#+begin_src rust
#[rustler::nif]
async fn transaction_query(tx_resource: ResourceArc<TransactionResource>, ...) {
    let tx = tx_resource.tx.as_ref().expect("Transaction finished");
    // do stuff with tx
}
#+end_src

*** Commit/rollback transaction (NIF)

#+begin_src rust
#[rustler::nif]
async fn transaction_commit(tx_resource: ResourceArc<TransactionResource>) {
    let mut tx_resource = Arc::get_mut(&mut tx_resource).unwrap(); // or get exclusive
    let tx = tx_resource.tx.take().expect("Already committed");
    // Drop order is critical: tx must go out of scope BEFORE we put the conn back!
    let conn = tx.commit().await.expect("Commit failed");
    // Now put Connection back into ConnectionResource for reuse
    let mut guard = tx_resource.conn_resource.0.write().await;
    debug_assert!(guard.is_none());
    *guard = Some(conn);
}
#+end_src
- Ditto for rollback.
